## 已覆盖的生产检查

Docker 部署自检会覆盖：

- Docker daemon 与 Docker Compose 可用性。
- `.env` 是否存在、文件权限是否安全、关键密钥是否弱值或缺失，以及 `ALLOWED_ORIGINS` 是否为空同源部署或真实生产来源。
- 备份签名密钥 `BACKUP_SIGNING_SECRET` 和备份加密密钥 `BACKUP_ENCRYPTION_SECRET` 是否已配置为随机强密钥。
- `.env` 中的 `IMAGE_TAG` 是否与 api/web 实际运行镜像标签一致，并确认运行镜像来源来自 3DPartHub GHCR 仓库。
- `api`、`web`、`postgres`、`redis` 容器运行状态、健康状态和镜像信息；API 应用进程是否以非 root 用户运行（entrypoint pid1 为 root 做迁移属正常，应用进程应经 su-exec 降权为 node），避免镜像入口脚本回退后扩大生产容器权限风险。
- 核心容器是否有近期 OOMKilled 或重启次数较高的风险信号；出现时默认生产验收不通过。
- 核心容器是否配置 healthcheck；缺少 healthcheck 会作为警告，默认生产验收不通过。
- Compose 文件中核心服务是否声明 `healthcheck` 和 `restart: unless-stopped`，避免部署配置缺少健康探针或重启自恢复策略。
- Compose 服务键是否存在重复，避免重复的 `restart`、`image`、`volumes`、`healthcheck` 等键被 YAML/Compose 解析覆盖。
- 当前运行容器重启策略是否实际生效 `restart: unless-stopped`，避免 Compose 修复后容器未重建导致重启不自恢复。
- Compose 文件与当前运行容器是否启用 `json-file` 日志轮转并配置 `max-size` / `max-file`，避免容器日志长期增长占满生产磁盘。
- Compose 持久化挂载是否完整，覆盖 `pgdata`、`uploads-data`、`static-data`、`redis-data` 和宿主机备份目录 bind mount。
- Compose API 关键环境是否声明完整，覆盖数据库连接、Redis 连接、JWT、备份签名/加密密钥和 API CORS 允许来源，避免重建容器时关键配置漏传。
- Compose 镜像来源是否正确，确认 `api` / `web` 指向 3DPartHub API/Web 镜像并使用 `IMAGE_TAG`，避免部署文件被改成错误镜像或旧镜像。
- Compose 资源限制是否声明完整，确认 `api`、`web`、`postgres`、`redis` 都带有 `mem_limit` 和 `cpus`，避免低配服务器上容器无上限抢占资源。
- API 停止宽限期是否在 Compose 和运行容器中生效，要求 `api.stop_grace_period` 至少 `5m` 且运行容器 `StopTimeout>=300s`，避免备份、恢复、上传或转换任务在重启/升级时被 Docker 过早终止。
- Compose 内部网络是否声明完整，确认 `api`、`web`、`postgres`、`redis` 都绑定 `internal` 网络且顶层 `networks.internal` 存在，避免核心服务脱离预期内部网络。
- Compose 端口暴露是否受控，确认只有 `web` 声明宿主机 `ports`，`api`、`postgres`、`redis` 不直接暴露到公网。
- 运行容器资源限制是否实际生效并与 `.env` 一致，确认 `api`、`web`、`postgres`、`redis` 都有正确的内存和 CPU 限制，避免 Compose 或资源预算修复后容器未重建。
- Redis healthcheck 是否通过 `REDISCLI_AUTH` 执行认证 ping，避免 Redis 开启密码后容器一直处于 unhealthy。
- 资源配置是否适配当前服务器内存档位，覆盖容器内存上限、API worker、转换并发、数据库连接数、API shm 和 Redis maxmemory。
- 实际运行容器的 Docker Mounts 是否与 Compose 持久化挂载一致，并确认 web 对静态/上传卷为只读挂载。
- 实际运行容器中的关键环境是否与 `.env` 一致，覆盖 API 数据库连接、API Redis 连接、API JWT 密钥、API CORS 允许来源、API 备份签名/加密密钥、PostgreSQL 密码和 Redis requirepass。
- PostgreSQL 当前密码、数据库迁移状态和 Redis 密码是否可用，确认 API 镜像内 Prisma migrations 与生产数据库一致，避免升级后数据库结构停在旧版本或出现 schema drift。
- Compose `web.ports` 是否把 `.env` 中的 `PORT` 映射到容器 `80/tcp`，运行中的 `3dparthub-web` 是否实际生效同一映射，并确认 `3dparthub-api`、`3dparthub-postgres`、`3dparthub-redis` 没有宿主机端口绑定；出现宝塔/nginx 占用、无监听、Compose Web 端口映射异常、Web 容器端口映射异常或运行容器端口暴露异常时会进入验收风险；同时覆盖 `/api/health`、`/api/health/ready`、`/api/health/live`、`/api/health/deep` 未登录访问控制、`/api/settings/version`、`/healthz`、API/Web 安全响应头、Web 首页入口、Web 前端静态资源和 Web 敏感路径直连暴露。
- 管理健康接口是否受控，`/api/health/deep` 未登录不能返回 `2xx`，避免公开数据库、Redis、存储和内部诊断信息。
- 运行版本是否可读取，固定 `IMAGE_TAG` 时 `/api/settings/version` 返回版本必须与标签一致，避免发布后容器仍跑旧镜像或 `/app/VERSION` 丢失。
- Web 敏感路径是否拒绝直连访问，自检会通过临时探针验证备份包、原始模型、图纸、附件、HTML 预览、批量任务、恢复快照、上传目录和 X-Accel 内部下载路径不会返回可下载内容，避免外部反代或旧 Web 镜像直接暴露业务文件。
- 宿主机备份目录 `./server/static/backups` 是否可创建并清理探针文件。
- 备份恢复演练证据是否存在且最近 30 天内有效；自检只读取 `.restore-drills/latest.json` 并给出预警，不会自动执行恢复演练。
- API 容器运行目录 `/app/uploads`、`/app/static`、`/app/static/backups` 是否可写。
- 宿主机部署目录磁盘/inode、Docker 数据目录磁盘/inode、备份目录磁盘/inode、API 数据卷容量、内存和备份目录状态。
- API/Web 最近日志是否包含常见启动、入口或静态资源错误；API 日志还会检查生产安全警告。

生产证据包验收会额外覆盖：

- 证据包必须包含健康报告、结构化 JSON、Compose 状态、API/Web 日志尾部、Docker/宿主机资源、网络监听、备份库存、版本/镜像追踪、README 和 `manifest.json`。
- 一键部署遇到 Compose 启动失败、初始健康检查失败或部署自检失败时，会自动尝试生成 `deploy-evidence-failed-*.tar.gz` 和同名 `.sha256`，避免生产启动故障只留下终端片段。
- `manifest.json` 的文件大小和 SHA-256 必须与证据文件一致。
- Compose 服务清单、Compose 状态、Docker 容器概览、Docker 存储概览和 README 必须符合预期结构，避免空壳辅助证据混入验收。
- 备份库存证据会只读列出备份目录、`directoryExists` 目录摘要、最近备份元数据、归档是否存在、企业级清单版本、签名/哈希字段是否存在、孤儿归档、`workDirs` 临时工作目录数量和最近一次恢复演练状态，方便判断生产是否具备可追溯备份现场；证据采集本身不执行恢复演练。缺少 `directoryExists` 或 `workDirs` 摘要时，验收器会把备份库存风险提升为中风险，避免截断或手工拼包证据被误判为完整。
- 备份库存采集按最近修改时间读取元数据和归档，已覆盖中文或含空格备份文件名，避免生产现场证据因为文件名拆词或排序偏差而漏报备份记录、孤儿归档或把较旧备份排在前面。
- 主健康报告 `deploy-health-report.json`、`manifest.json`、`README.txt` 和 `deployment-provenance.txt` 必须包含一致的证据批次 ID，避免不同采集批次的文件被拼接后误验收。
- JSON/TXT 健康报告一起验收时，TXT 中的 Compose 文件、环境文件、证据批次和汇总计数必须与 JSON 对齐，避免新旧报告混用。
- 采集脚本会对日志片段和命令输出中的常见密钥、连接串和 `Authorization` 头做敏感信息脱敏；验收器会拒绝明显的密钥赋值、带密码的连接串或未脱敏认证头。
- 同名 `.tar.gz.sha256` 是生产 `.tar.gz` 证据包的默认必需项；验收器会校验证据包归档本身的 SHA-256，并要求摘要内容引用当前 `.tar.gz` 文件名，再把期望/实际摘要写入验收 JSON，降低传输损坏、裸 digest 混用或拿错文件的风险。
- 验收 JSON 会写入 `productionEvidence.finalConclusionReady`，用于区分完整生产证据闭环和报告兜底验收；默认 `deploy:acceptance` 会强制该字段为 `true`，明确使用兜底参数时除外。最终生产闭环还要求 `productionEvidence.backupInventoryReady=true`，避免完整证据包在备份库存中风险、残留 `.work` 临时工作目录或缺少恢复演练时被误判为可上线结论。
- 验收摘要会写入 `backupInventory`，包含 `riskLevel`、`nextActions` 和 `restoreDrillExecuted`，并在 Markdown 结论表展示备份库存概览、风险等级、备份库存闭环与备份恢复演练状态，避免只把备份现场藏在原始证据文件里。缺少有效恢复演练、演练时间无效、最近演练超过 30 天或存在备份临时工作目录时，备份库存风险会提升到中风险，默认生产验收不会通过最终闭环。
- 健康报告必要检查必须一项一条且位于 pass 信息开头；验收器会拒绝缺失、重复、非 pass 状态、伪造前缀或把多个必要项合并到同一条 pass 信息里的报告。
- 证据包只允许固定白名单文件，并拒绝 `.env`、额外文件、重复报告、符号链接、特殊文件和不安全路径。
- 报告默认必须不超过 `24` 小时，且默认不接受警告项。
- `deployment-provenance.txt` 会记录包版本、Git 提交、`IMAGE_TAG` 和核心容器镜像 ID；验收器要求 `api`、`web`、`postgres`、`redis` 都包含 `image=`、`imageId=sha256:`、`status=`、`health=`、`restartPolicy=`、`restartCount=` 和 `oom=`，并拒绝密钥赋值，便于把健康证据关联到具体发布。

## 本地验证记录

当前本地已使用以下命令验证：

```bash
npm run verify:enterprise
npm run deploy:wiring:verify
npm run verify:deploy
npm run verify:local
npm --prefix server test
npx prettier --check README.md deploy/README.md docs/运行环境规范.md docs/部署健康验收清单.md docs/代码维护规范.md scripts/verify-deploy-health-report.mjs scripts/verify-deploy-wiring.mjs .github/workflows/docker-build.yml .github/workflows/ci.yml .github/pull_request_template.md package.json
git diff --check
```

`npm run verify:enterprise` 会依次执行 Prettier 检查、`RUN_SERVER_TESTS=1 npm run verify:local` 和 `git diff --check`，通过后生成 `local-enterprise-acceptance.md` 与 `local-enterprise-acceptance.json`；任一步失败也会覆盖写入 `result=failed`、失败步骤和剩余风险，避免仓库里残留旧的 `passed` 摘要被误当成发布前通过证据。摘要中的“生产证据闭环状态”会写入 `productionEvidence`，自动标记是否已存在 `deploy-health-acceptance.json`、是否满足 `finalConclusionReady=true`、最新 `deploy-evidence-*.tar.gz` 是否有同名 `.sha256`、是否只有失败证据包，以及下一步该采集还是执行 `deploy:acceptance`。这些命令证明本地脚本、文档 wiring、前后端构建、静态检查、部署工具回归和服务端单测通过；它们不能替代真实生产服务器的容器、端口、密码、磁盘、内存和日志证据。

## 生产验收步骤

在生产服务器实际部署目录执行：

```bash
cd /opt/3dparthub
sh scripts/collect-deploy-evidence.sh
```

最终生产结论要求最近一次备份恢复演练纳入证据，先在维护窗口执行：

```bash
cd /opt/3dparthub
docker-compose exec api npm run backup:e2e
sh scripts/collect-deploy-evidence.sh
```

演练成功后会写入 `server/static/backups/.restore-drills/latest.json`，证据包中的 `backup-inventory.txt` 会出现 `Restore drill evidence: status=passed`。

把生成的 `deploy-evidence-YYYYMMDD-HHMMSS.tar.gz` 和同名 `.tar.gz.sha256` 一起回传到仓库后执行：

```bash
npm run deploy:acceptance -- deploy-evidence-YYYYMMDD-HHMMSS.tar.gz
```

验收通过后应保留生成的 `deploy-health-acceptance.md` 和 `deploy-health-acceptance.json` 到公司内部运维归档。仓库默认忽略这些文件，避免误提交主机名、部署路径、端口和日志片段。

## 剩余风险

- 生产证据包尚未回传前，不能声明 Docker 部署健康目标最终完成。
- 本地企业级验收摘要会持续显示 `productionEvidence.finalConclusionReady`；只有该字段来自完整生产证据包验收且为 `true`，才能把生产部署健康结论视为已闭环。
- `deploy:acceptance` 能验证当前时间点的部署快照；生产重启、升级、恢复备份、修改 `.env`、调整反代或迁移数据后需要重新采集证据。
- 自检能发现默认弱密钥、备份签名/加密密钥缺失、容器健康、资源配置过载、宿主机备份目录可写性、运行目录权限、磁盘/内存和 API/Web 常见日志错误；如果未先执行 `docker-compose exec api npm run backup:e2e`，证据包仍不能证明备份已恢复演练，默认生产验收不会给出最终生产闭环结论。
- 证据包故意不包含 `.env`，并会脱敏/拒绝明显敏感文本；密钥具体内容仍需由运维侧妥善保存和轮换。
- 如果只能回传 JSON/TXT 报告并使用 `--allow-report-only`，必须同时提供 `--require-text deploy-health-report.txt`，但仍不能证明 Compose 状态、API/Web 日志尾部、Docker/宿主机资源、网络监听、备份库存、版本/镜像追踪和 manifest 哈希未被篡改。
- 如果旧证据包缺少 `.tar.gz.sha256` 并使用 `--allow-missing-sidecar`，不能证明归档在传输后仍与服务器生成时完全一致，只能依赖归档内部 manifest 校验证据文件。

## 后续维护规则

- 修改一键部署、自检、证据采集、验收器、Docker 镜像发布或相关文档后，必须执行 `npm run verify:deploy`。
- 提交或发布前执行 `npm run verify:enterprise` 生成本地验收摘要；只需要较轻量检查时执行 `npm run verify:local`，涉及服务端行为时同时执行 `npm --prefix server test`。
- 如果新增生产检查项，需要同步更新 `scripts/verify-deploy-health-report.mjs` 的必要检查、`scripts/test-deploy-health-check.sh` 的回归用例和本文档。
