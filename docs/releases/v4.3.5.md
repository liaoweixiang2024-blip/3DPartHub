## 更新标题

3DPartHub v4.3.5 - 修复生产恢复大备份包报 spawnSync tar ENOBUFS（maxBuffer 扩容）

## 标签描述

3DPartHub v4.3.5 fixes the production restore failure "spawnSync tar ENOBUFS". Root cause: restore pre-checks call execFileSync('tar tvzf'/'tzf') and read the manifest via 'tar xOzf' with Node's default 1MB maxBuffer. Since v4.3.0 expanded backup scope to full model files, archives carry thousands of entries and the tar listing output now exceeds 1MB, so the very first safety check threw ENOBUFS and aborted the restore before any data was touched. Fix: all output-capturing child processes in the backup/restore path (tar tvzf/tzf/xOzf, psql full-database restore, docker cp, prisma migrate deploy/db push) now set maxBuffer to 512MB, plus a 200k-entry sanity cap on tar listings (corrupted archives rejected instead of exhausting memory). Also fixes a startup TDZ ReferenceError in cleanupExpiredSafetySnapshots (module-level call accessed a const declared later in the file, so expired safety snapshots were never actually cleaned; now deferred via setTimeout). Regression test builds a real 15,000-entry tar.gz whose listing exceeds 1MB and asserts the safety check passes. Verified end-to-end locally: 1.31GB / 6,332-entry archive restored fully (1,319 models, 56 categories, all file directories) with no ENOBUFS. No DB migration.

## 更新描述

本次为**关键修复**，无数据库迁移。

**问题**：生产服务器恢复备份时报 `spawnSync tar ENOBUFS`，恢复无法开始。

**原因**：恢复前的安全检查需要读取备份包的文件列表（`tar tvzf`）。Node 的 `execFileSync` 默认只允许子进程输出 **1MB**——v4.3.0 起备份包含全部模型文件，包内条目数千、列表输出超过 1MB，检查直接抛错中断。同类隐患还有：读备份清单（`tar xOzf`）、数据库整库导入（psql 每条语句一行输出，大库十万行就会超）、prisma 迁移输出。

**修复**：

- 备份/恢复链路上所有捕获输出的子进程（tar 列表/清单、psql 导库、docker cp、prisma migrate）**缓冲上限统一放大到 512MB**
- tar 列表新增 **20 万条目数上限**：损坏/异常的包直接拒绝恢复，不会无限吃内存
- 顺带修复一个启动警告：过期安全快照的清理函数在模块加载期因声明顺序抛 ReferenceError（实际从未清理过），改为延迟执行

**验证**：本地 1.31GB / 6332 条目真实备份包完整恢复（1319 个模型、56 个分类、全部文件目录），全程无报错；新增回归测试构造 15000 条目（列表输出 >1MB）的 tar 包断言检查通过。

**建议升级后验证**：服务器上重新发起之前失败的恢复，应能正常走完。
