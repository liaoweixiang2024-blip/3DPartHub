## 更新标题

3DPartHub v4.3.3 - 备份下载彻底摆脱 nginx 挂载依赖 + 数据卷名固定（防"数据消失"假象）

## 标签描述

3DPartHub v4.3.3 hardens backup downloads at the source level so they can never break due to nginx mount drift again. Backup archive downloads previously rode nginx X-Accel-Redirect: the API validated the one-time token and handed the file to nginx via the internal /\_protected_static/ location — but the backups directory is the only bind-mounted path in the stack, and when the web (nginx) container's view of it drifts from the api's (exactly what caused the production 404 "未发现文件" incident), nginx returns 404 while the API has no way to detect it. The fix adds a forceStream option to sendAcceleratedFile and enables it on the backup download route: backup downloads now stream directly from Node (createReadStream with HTTP Range support), eliminating the nginx dependency entirely — the compose web mount from v4.3.2 becomes pure belt-and-braces. Model/drawing/ticket/inquiry downloads keep their accelerated path (their files live in shared named volumes, no drift risk). A new "备份下载通道" (download channel) item appears in the backup policy check, verifying the latest archive is readable and surfacing issues before an admin hits a failed download. Second hardening: docker-compose volumes now carry explicit fixed names (3dparthub_pgdata etc.) — compose's default directory-prefixed volume naming meant launching from a renamed/moved directory would silently attach a fresh set of EMPTY volumes, creating a "all data lost" illusion (real data stays in the old volumes). With explicit names, any directory any future deploy uses attaches the same volumes. 3 new unit tests (forceStream bypasses accel, default accel behavior preserved for other callers, Range on stream path). No DB migration.

## 更新描述

本次为**加固更新**，无数据库迁移。两个源码级加固，从根上杜绝这次生产事故的两类问题。

**加固一：备份下载不再依赖 nginx 挂载（彻底修复下载 404）**

- 之前：备份下载走 nginx 加速通道（API 校验后让 nginx 发文件）。备份目录是全站唯一宿主机挂载，一旦 web 容器没挂到这个目录（v4.3.2 之前的情况），nginx 404 而 API 毫无感知 → 「未发现文件」
- 现在：备份下载改为 **API 直连流式下发**（支持断点续传 Range），下载链路完全不经过 nginx 文件系统——**无论容器挂载怎么配，备份下载都能工作**
- 模型/图纸/工单附件下载仍走原加速通道（它们在双容器共享的数据卷里，无此风险，行为不变）
- 备份体检新增「**备份下载通道**」检查项：验证最近备份文件可读，有问题在体检页直接暴露，不用等点下载才发现

**加固二：数据卷显式命名（防"数据全部丢失"假象）**

- 之前：数据卷名默认带**目录名前缀**（如 `/opt/3dparthub` → `3dparthub_pgdata`）。若换了目录名/位置启动，compose 会静默创建一套**全新的空卷**连上去——站点看起来"数据全没了"（真实数据仍在旧卷里，但很难发现）
- 现在：docker-compose.yml 里 4 个数据卷显式固定命名（`3dparthub_pgdata` 等）。**无论部署目录叫什么、在哪，永远接同一组数据卷**。与现有生产卷名一致，升级无感

**建议升级后验证**：设置 → 数据备份 → 点「下载」（应正常）；点「策略体检」应出现「备份下载通道：正常」一行。

前端「检查更新」会读取本更新描述展示最新版本号与更新内容。

## 部署备注

```bash
cd /opt/3dparthub
docker-compose pull
docker-compose up -d
# 更新后强制刷新浏览器：Cmd+Shift+R（Mac）或 Ctrl+Shift+R（Windows）
```

> **本次还需手动同步一处 docker-compose.yml 改动（数据卷显式命名）**：把文件末尾的 `volumes:` 段替换为：
>
> ```yaml
> volumes:
>   pgdata:
>     name: 3dparthub_pgdata
>   uploads-data:
>     name: 3dparthub_uploads-data
>   static-data:
>     name: 3dparthub_static-data
>   redis-data:
>     name: 3dparthub_redis-data
> ```
>
> 这些名字与当前生产卷名**完全一致**（`docker volume ls` 可核对），替换后 `docker-compose up -d` 无感。以后无论在哪个目录启动都接同一组卷。

默认跟随 latest 的部署由 Watchtower 自动更新（compose 卷名段仍需手动同步一次）。
