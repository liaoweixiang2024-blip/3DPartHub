## 更新标题

3DPartHub v3.5.6 - 备份恢复崩溃自愈（恢复硬中断可自动检测 + 一键回滚；修复影响所有恢复回滚的幂等性 bug）

## 标签描述

3DPartHub v3.5.6 hardens the **backup/restore crash-recovery path**. Server-only, no DB migration, no breaking change, no front-end logic change.

**Why this release**: a restore runs a destructive `resetDatabaseSchema` (DROP + CREATE) before loading the backup. If the process was hard-killed mid-destructive (SIGKILL / OOM / power loss), the DB was left in an empty-schema broken state AND the safety snapshot lived only in a temp dir that the next startup wiped — so the pre-restore data was lost with no automatic recovery. v3.5.6 closes that gap and fixes a related latent bug found while testing it.

1. **[Important] `resetDatabaseSchema` is now idempotent (`DROP SCHEMA IF EXISTS`)**: the rollback safety net (`rollbackToSafetySnapshot`) re-runs `resetDatabaseSchema`, whose first statement was `DROP SCHEMA public CASCADE` with `ON_ERROR_STOP=1`. In the crash scenario the `public` schema was already gone, so the DROP errored _"schema public does not exist"_ and **the entire rollback aborted** — meaning every restore-failure rollback (not just crash recovery) could fail to recover. This was latent because the e2e tests only covered successful restores, never the rollback branch. Now `DROP SCHEMA IF EXISTS public CASCADE` works whether `public` exists or not.
2. **[Important] Pre-restore snapshot is persisted durably before the destructive phase**: a copy of the safety snapshot is written to `_safety_snapshots/` plus a `.restore_in_progress_<jobid>.json` marker file, so a hard crash no longer loses the rollback credential (the temp-dir copy would be wiped by `cleanupStaleBackupWorkDirs`).
3. **[Medium] Startup detects an interrupted restore and alerts**: on boot, `detectInterruptedRestores()` scans for leftover markers and logs a CRITICAL error with the preserved snapshot path and recovery instructions, so a silently-broken DB is never missed.
4. **[Medium] One-click recovery endpoint**: admins can roll back via `POST /api/settings/backup/recover-interrupted { durableSnapshot }` (and `GET /api/settings/backup/interrupted-restores` to list). The marker is auto-cleared and the consumed snapshot deleted once recovery succeeds. No automatic destructive rollback is ever taken on ambiguous state — the admin decides.

Marker lifecycle precisely brackets the "DB may be broken" window: set before the destructive reset, cleared once the DB import succeeds or the rollback succeeds. Module restores are unaffected (they use transactional TRUNCATE, which PostgreSQL auto-aborts on a hard crash).

Verified end-to-end against a throwaway database (dev DB untouched): simulated a hard crash by dropping the schema mid-restore → marker + durable snapshot survived → recovery restored all 28 tables and data → marker auto-cleared. Server 142 unit tests green.

## 更新描述

本次是**备份/恢复的崩溃自愈加固**,纯服务端,无数据库迁移、无破坏性变更、无前端逻辑改动。

恢复在导入备份前会跑一次破坏性的「重置数据库 schema」(DROP + CREATE)。如果进程在这期间被 **强杀 / OOM / 断电** 硬中断,数据库会卡在空 schema 的破损态,而且回滚用的安全快照原本只放在临时目录里——下次启动会被当成垃圾清掉,**恢复前的数据就找不回来了**。v3.5.6 补上了这个缺口,并修了测试时连带挖出的一个老 bug。

- **[重要] 修复影响所有「恢复失败回滚」的 bug**:回滚安全网会再跑一次重置 schema,而它的第一句 `DROP SCHEMA public CASCADE` 配合 `ON_ERROR_STOP=1` 在崩溃恢复场景下会因为「public 已不存在」直接报错,**导致整个回滚中断**——也就是说不只是崩溃恢复,任何恢复失败时的回滚都可能失效。这个 bug 一直潜伏,因为自动化测试只覆盖了「恢复成功」,从没走到回滚分支。现已改为幂等的 `DROP SCHEMA IF EXISTS`。
- **[重要] 恢复前安全快照持久化**:进入破坏性阶段前,把安全快照复制一份到 `_safety_snapshots/` 并写一个 marker 文件,硬崩后回滚凭据不再丢。
- **[中] 启动检测中断的恢复**:服务启动时扫描残留 marker,有就打 CRITICAL 告警,带上快照路径和恢复指引——破损数据库不会被悄悄忽略。
- **[中] 一键恢复端点**:管理员可用 `POST /api/settings/backup/recover-interrupted` 回滚(`GET /interrupted-restores` 列出可恢复项),恢复成功后 marker 自动清除、快照自动清理。**绝不自动做破坏性回滚**——由管理员确认后再执行。

marker 生命周期精确覆盖「数据库可能破损」的窗口(破坏性前写入、数据库导入成功或回滚成功后清除)。模块恢复不受影响(它用事务性 TRUNCATE,硬崩时 PostgreSQL 会自动回滚)。

已在一次性测试库上端到端验证(开发库未动):模拟硬崩(中途 DROP schema)→ marker 和持久快照存活 → 恢复后 27 张业务表 + 数据全部还原 → marker 自动清除。服务端 142 单测全绿。
