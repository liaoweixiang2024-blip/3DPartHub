## 更新标题

3DPartHub v4.4.0 - 批量上传四项修复 + 拖文件夹直传 + 单零件压缩包命名 + 恢复链路流式加固

## 标签描述

3DPartHub v4.4.0 fixes four batch-upload bugs, adds drag-and-drop folder upload, corrects single-part archive naming, and hardens the backup/restore pipeline. Batch upload: models beyond the 200-per-archive cap now report explicit "skipped" results instead of vanishing silently (their same-name PDFs also stopped mis-reporting "model not found"); nested-subfolder PDFs skipped by the folder-priority rule now report skipped too; RAR preflight no longer double-counts PDF bytes when one directory holds multiple models (which could falsely reject large archives as over-limit); stray root-level PDFs no longer break single-part-archive detection. New feature: drag a part folder straight into the upload dialog — the client expands it via the FileSystem entry API (preserving relative paths), filters to model formats + PDF (ignoring GPUCache/hidden files), packs an in-memory ZIP with JSZip (STORE mode), and uploads through the existing batch channel, inheriting all server rules (folder name as model title, variant-skip, PDF pairing, category resolution). Single-part archives (folder/file.STEP with a unique stem) are now detected regardless of whether a category was pre-selected — previously the folder name was mistaken for a category and auto-created a new root category, with the model title degraded to the raw filename; two-level paths with no existing root category no longer auto-create one, while three-level library-tree uploads keep auto-creating categories. Backup/restore hardening: the pre-restore safety check (tar tvzf) is now streaming — memory grows linearly with entry count and the 1M-entry cap no longer applies on the main restore path; psql import runs with -q and discards stdout (previously every statement's status line was buffered in memory — multi-million-statement restores could hit ENOBUFS and abort); docker cp of the SQL dump now uses the full restore timeout instead of a hard 30s; streaming scans truncate stderr accumulation. Verified end-to-end: a real 2.4GB / 12,521-entry backup restored fully (2,643 models, 58 categories, 639 drawings) with no errors. Client adds jszip + patch-package (the jszip type shim strips a node-types reference that polluted browser globals). No DB migration.

## 更新描述

本次为**功能 + 修复**版本，无数据库迁移。

**新功能：上传弹窗支持直接拖文件夹**

- 把零件文件夹（内含 STEP + PDF）直接拖进上传框：自动展开（保留相对路径）→ 过滤（只收模型格式和 PDF，忽略 GPUCache/隐藏文件/SLDPRT 源文件）→ 内存打包 ZIP → 走批量上传通道
- 完整继承批量上传规则：**模型标题 = 文件夹名**、变体子夹自动跳过、PDF 自动挂载同名模型、不自动建分类
- 兼容所有浏览器（JSZip 方案）；拖文件/压缩包的行为完全不变

**单零件压缩包命名修复**

- 上传「文件夹/文件.STEP」形态的压缩包时，模型标题现在正确使用**文件夹名**（如「半自锁公头\_PM20」）
- 之前若没先选分类，文件夹名会被误当成分类名自动新建根分类，标题退化成纯文件名
- 三层及以上的零件库树形态（分类/零件/文件）维持自动建分类，批量上传不受影响

**批量上传四项修复**

1. **超 200 个模型不再静默丢失**：超出上限的逐条提示「超出单包 200 个模型上限，请拆分后重新上传」（此前直接消失，且其 PDF 被误报「未找到同名模型文件」）
2. **被跳过的子文件夹 PDF 有反馈**：提示「零件目录已有直接 PDF，子文件夹 PDF 已跳过」（此前静默消失）
3. **RAR 大包误拒修复**：同一目录多个模型共享的 PDF 体积此前被重复累计 N 次，导致误报「解压总量超限」
4. **包根散落 PDF 不再破坏识别**：包根的说明.pdf 不会再让单零件包检测失效

**备份/恢复加固（大库场景）**

- 恢复前安全校验改为**流式扫描**：内存随条目数线性增长，恢复主链路不再有条目数上限
- psql 导库加 `-q` 静默并丢弃输出：此前每条语句的状态行全量进内存，千万行级大库会 ENOBUFS 中断恢复
- docker cp 拷贝 SQL 文件的 30 秒硬超时改为整库恢复超时（60 分钟）兜底
- 实测：2.4GB / 12521 条目真实备份包完整恢复（2643 模型、58 分类、639 图纸）无损

**建议升级后验证**：拖一个零件文件夹试试上传；在服务器上做一次备份 → 恢复演练。
