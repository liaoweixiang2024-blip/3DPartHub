## 更新标题

3DPartHub v4.5.3 - 修复备份恢复到其他机器后回收站模型误报「文件缺失」无法恢复

## 标签描述

3DPartHub v4.5.3 fixes recycle-bin restore being wrongly blocked after restoring a backup onto a different machine. The models table stores upload_path as the absolute path from the machine where the upload happened — when a backup made on machine A is restored onto server B, every restored model's upload_path still points at A's filesystem. The recycle bin checked file existence with that raw path only, so all such models showed「文件缺失」and restore returned 409, even though the actual files were correctly restored into static/originals/{id}.{format}. Both checks (the can_restore flag in the deleted-models list and the restore endpoint's 409 guard) now use the same findOriginalModelPath fallback that the download feature already uses: try upload_path first, fall back to the conventional static/originals/{id}.{ext} location. Server-native uploads are unaffected; no data repair needed — after upgrading, previously "missing" models become restorable as-is. No DB migration.

## 更新描述

本次为**回收站修复**版本，无数据库迁移。

**备份跨机恢复后，回收站不再误报「文件缺失」**

- **原因**：`models` 表的 `upload_path` 存的是上传方的绝对路径。本地备份恢复到服务器后，路径仍指向本机（如 `/Users/xxx/...`），服务器上不存在；回收站的文件检查只看这个原始路径，于是所有恢复来的模型都显示「文件缺失」、无法恢复——**但文件本体其实完好在 `static/originals/` 里**（模型下载等功能一直都能正常下到原文件）
- **修复**：回收站两处检查（列表的 `can_restore` 标记 + 恢复接口的拦截）改用与下载功能相同的 `findOriginalModelPath` 回退逻辑：先按 `upload_path` 找，失效则回退到约定位置 `static/originals/{id}.{格式}`
- **效果**：升级后，此前显示「文件缺失」的模型直接变为可恢复，无需任何数据修复操作；服务器本机上传的模型行为不变
