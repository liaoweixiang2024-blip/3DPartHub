## 更新标题

3DPartHub v3.5.7 - 跨服务器迁移恢复修复（签名校验失败可强制恢复 + 报错指引 + 迁移密钥文档）

## 标签描述

3DPartHub v3.5.7 fixes the **cross-server backup-restore portability gap**. Every backup's `.json` record carries an HMAC signature computed with `BACKUP_SIGNING_SECRET || JWT_SECRET`. The list-based restore verifies it, so restoring a backup on a freshly-deployed new server (which generated new random secrets) aborted with _"签名校验失败"_ — blocking the documented migration flow. No DB migration, no breaking change.

1. **[Important] Optional "skip signature" force-restore for migration**: `RestoreJob.force` threads through `startRestoreJob` → the worker → `runRestore`; when set, the HMAC signature check is skipped (the file-integrity SHA256 is still enforced, so content corruption/tampering is still caught). Surfaced as a 「跨服务器迁移：跳过签名校验」checkbox in the restore confirmation dialog, and as a `force` body param on `POST /api/settings/backup/restore/:id`.
2. **[Medium] Actionable signature-failure error**: `assertBackupSignature` now explains both likely causes — cross-server secret mismatch vs tampering — and lists the three remedies (carry over `BACKUP_SIGNING_SECRET`, use the force checkbox, or use the import-file path which never checks signature). Previously the generic _"文件记录可能被篡改"_ misled legitimate migration users.
3. **[Medium] Migration secret documentation**: `docker-compose.yml` migration section and `.env.example` now state that `BACKUP_SIGNING_SECRET` (and `BACKUP_ENCRYPTION_SECRET` if encryption was enabled) must be carried from the old server to the new `.env`, plus the two alternative paths.

Backup data itself is fully self-contained (pg_dump + all local files + manifest SHA256, no embedded hostnames or absolute paths), so cross-server restore is safe once the signature gate is handled.

Verified: server 142 + client 12 unit tests green.

## 更新描述

本次修复**跨服务器迁移时备份恢复会被签名校验挡住**的问题。每个备份的 `.json` 记录都带 HMAC 签名(用 `BACKUP_SIGNING_SECRET`,没设则用 `JWT_SECRET`),而列表式恢复会校验签名——所以把备份恢复到一台**全新部署**的新服务器(密钥是新生成的随机值)会报「签名校验失败」中断,正好卡住文档里写的迁移流程。无数据库迁移、无破坏性变更。

- **[重要] 恢复确认里新增「跨服务器迁移：跳过签名校验」勾选框**:勾上后跳过 HMAC 签名校验(**文件完整性 SHA256 仍校验**,所以文件损坏/被改还是能发现)。后端 `POST /api/settings/backup/restore/:id` 也支持 `force` 参数。
- **[中] 签名校验失败的报错改成可操作的**:现在会说明两种可能原因——跨服务器密钥不一致 vs 真篡改,并列出三条出路(把旧服务器 `BACKUP_SIGNING_SECRET` 复制过来 / 勾选跳过签名 / 用「导入恢复」直接传 .tar.gz)。以前那句"可能被篡改"对正常迁移用户很有误导性。
- **[中] 迁移密钥文档补全**:`docker-compose.yml` 的迁移段落和 `.env.example` 现在写清了——迁移到新服务器要把旧服务器的 `BACKUP_SIGNING_SECRET`(若启用过加密还有 `BACKUP_ENCRYPTION_SECRET`)原样复制到新 `.env`,以及两条替代路径。

备份数据本身完全自包含(数据库 + 全部本地文件 + manifest SHA256,不含主机名/绝对路径),跨服务器迁移是安全的,只需处理好这道签名关。
