# 运行环境规范

这份规范用于区分本地开发、Docker 本地测试和生产部署。以后启动项目前先看这里，避免端口、数据库、Redis 和 Docker 模式混在一起。

## 结论

本项目固定使用三种运行模式：

| 场景             | 推荐模式                                      | 说明                                                                                        |
| ---------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 日常开发调试     | 前端本机源码 + 后端本机源码 + Docker 数据服务 | 前端 Vite 固定 `5173`，后端源码固定 `8000`，PostgreSQL/Redis 使用 Docker 端口 `5433`/`6380` |
| 本地完整容器测试 | Docker Compose local                          | 本机用源码构建 api/web 镜像，完整模拟容器部署                                               |
| 生产环境         | 纯 Docker Compose                             | web、api、postgres、redis 全部在 Docker 内运行                                              |

不要在同一个场景里混用多个端口或多个 Redis/PostgreSQL 容器。

## 本地开发调试

本地开发模式用于改代码、调页面、看接口日志。

推荐调试结构：

```text
client npm run dev      -> http://127.0.0.1:5173
Vite proxy /api         -> http://127.0.0.1:8000
server npm run dev      -> http://127.0.0.1:8000
PostgreSQL Docker       -> localhost:5433
Redis Docker            -> localhost:6380
```

默认情况下，`5173` 的 `/api`、`/static`、`/uploads` 会代理到本机后端 `8000`。Vite 已配置 `strictPort: true`，如果 `5173` 被占用会直接启动失败，不会自动漂到 `5174`、`5175`。

后端使用 [server/.env](../server/.env) 连接 Docker 数据服务：

```env
DATABASE_URL=postgresql://modeluser:modelpass@localhost:5433/3dparthub
REDIS_URL=redis://localhost:6380
```

启动顺序：

```bash
bash scripts/start-local.sh
```

这个一键脚本会自动启动 Colima，重启已有的 `3dparthub-postgres` / `3dparthub-redis`，缺失时创建；如果旧的本地前端或后端进程占用 `5173` / `8000`，会先结束旧进程再启动。

检查状态：

```bash
docker ps
lsof -nP -iTCP:5433 -sTCP:LISTEN
lsof -nP -iTCP:6380 -sTCP:LISTEN
curl http://localhost:8000/api/health
curl http://localhost:5173/api/health
curl http://localhost:5173/
CHECK_VITE=1 node scripts/check-local-stack.mjs
```

停止本机前端/后端时，停止对应 `npm run dev:local` 进程即可。数据库和 Redis 可以保留运行，避免频繁冷启动。

## 本地完整容器测试

本地完整容器测试用于确认 Docker 镜像构建、Nginx、容器网络和生产形态是否正常。

运行结构：

```text
web container      -> http://localhost:3780
api container      -> internal api:8000
PostgreSQL Docker  -> internal postgres:5432, host localhost:5433
Redis Docker       -> internal redis:6379, host localhost:6380
```

启动：

```bash
colima start
docker compose -f docker-compose.local.yml up -d --build
```

访问：

```text
http://localhost:3780
```

查看日志：

```bash
docker compose -f docker-compose.local.yml logs -f api
docker compose -f docker-compose.local.yml logs -f web
docker compose -f docker-compose.local.yml logs -f postgres
docker compose -f docker-compose.local.yml logs -f redis
```

停止但保留数据：

```bash
docker compose -f docker-compose.local.yml down
```

停止并删除本地测试数据：

```bash
docker compose -f docker-compose.local.yml down -v
```

只有明确要清空本地数据库和文件时才能使用 `down -v`。

## 生产环境

生产环境使用纯 Docker Compose，不使用 `npm run dev`，不使用 Vite 开发服务。

运行结构：

```text
web container
api container
postgres container
redis container
```

容器内部连接：

```env
DATABASE_URL=postgresql://modeluser:密码@postgres:5432/3dparthub
REDIS_URL=redis://redis:6379
```

生产环境对外入口默认是：

```text
http://服务器IP:3780
```

部署：

```bash
docker compose up -d
```

检查：

```bash
docker compose ps
docker compose logs api --tail 80
docker compose logs postgres --tail 80
docker compose logs redis --tail 80
curl http://localhost:3780/api/health
curl -fsSL -O https://raw.githubusercontent.com/liaoweixiang2024-blip/3DPartHub/main/scripts/deploy-health-check.sh
sh deploy-health-check.sh --report deploy-health-report.txt --json deploy-health-report.json
curl -fsSL -O https://raw.githubusercontent.com/liaoweixiang2024-blip/3DPartHub/main/scripts/collect-deploy-evidence.sh
sh collect-deploy-evidence.sh
```

生产复查必须在实际部署目录执行，默认读取当前目录的 `docker-compose.yml` 和 `.env`。如果 Compose 或环境变量文件不在当前目录，需要显式传入，例如 `sh deploy-health-check.sh --compose-file /opt/3dparthub/docker-compose.yml --env-file /opt/3dparthub/.env --report deploy-health-report.txt --json deploy-health-report.json`，避免自检没有读到真实生产配置。`deploy-health-report.txt` 用于人工排障，`deploy-health-report.json` 用于后续归档、比对或运维面板读取；核心容器未配置 healthcheck、最近发生过 OOMKilled、重启次数较高、`.env` 权限过宽、运行容器关键环境与 `.env` 不一致、api/web 运行镜像标签与 `IMAGE_TAG` 不一致、存活接口失败、API/Web 安全响应头缺失、Web 首页入口无法返回前端 HTML、Web 前端静态资源无法加载、API/Web 日志包含常见入口或启动错误、关键 Compose 持久化挂载缺失、Redis healthcheck 未使用 `REDISCLI_AUTH` 认证 ping、Compose/运行容器日志轮转缺失、运行容器重启策略未生效、部署目录或备份目录 inode 偏低、资源配置超过当前内存档位、实际容器挂载仍是旧配置，或 Compose 服务未设置 `restart: unless-stopped`，都会记为警告或失败，生产验收默认不接受。自检会确认备份签名/加密密钥已配置，并检查 API 容器实际环境中的 `BACKUP_SIGNING_SECRET`、`BACKUP_ENCRYPTION_SECRET` 是否与 `.env` 一致，避免备份可用但签名或加密密钥没有进入生产容器。自检会按服务器总内存复核 `API_MEMORY_LIMIT`、`API_WORKERS`、`CONVERSION_WORKER_CONCURRENCY`、`DB_CONNECTION_LIMIT`、`API_SHM_SIZE`、`REDIS_MAXMEMORY` 等资源配置，避免小内存机器因为过高并发或缓存上限反复 OOM。自检会用隐藏探针文件确认宿主机备份目录可写，并分别检查部署目录和备份目录的磁盘容量与 inode，避免备份目录独立挂载时权限、空间或小文件额度不足。`collect-deploy-evidence.sh` 会额外收集 Compose 状态、API/Web 日志尾部、Docker/宿主机资源、网络监听、备份库存和版本/镜像追踪信息，会对常见密钥、连接串和 `Authorization` 头做敏感信息脱敏，并生成不包含 `.env` 的证据包与同名 `.tar.gz.sha256` 摘要。生产验收 `.tar.gz` 默认要求该同名摘要一起回传，并要求摘要内容引用当前 `.tar.gz` 文件名；只有旧证据包遗失摘要时才使用 `--allow-missing-sidecar`。若指定 `--output-dir`，目录必须为空且不能是符号链接、路径穿越或以 `-` 开头的路径段，避免新旧证据混在一起或被错误打包。一键部署自检失败时会自动尝试生成 `deploy-evidence-failed-YYYYMMDD-HHMMSS.tar.gz` 和同名 `.sha256`。证据目录、健康报告和验收摘要已在 `.gitignore` 中忽略，避免误提交主机名、部署路径和日志片段。

最终生产验收默认要求最近一次备份恢复演练纳入证据，先在维护窗口执行 `docker compose exec api npm run backup:e2e`。演练成功后会写入 `server/static/backups/.restore-drills/latest.json`，随后采集的 `backup-inventory.txt` 会包含 `Restore drill evidence: status=passed`，验收摘要会显示“备份恢复演练已执行”。缺少演练、演练时间无效、超过 30 天，或备份目录残留 `.work` 临时工作目录时，`backupInventory.riskLevel` 会提升为中风险，`productionEvidence.finalConclusionReady` 不会为 `true`。该命令会真实创建备份、导入备份并恢复，生产环境执行前应确认外部副本和维护窗口。

把生产证据包或两份报告拷回仓库后，用下面命令做最终验收：

```bash
npm run deploy:acceptance -- deploy-evidence-20260526-120000.tar.gz
npm run deploy:report:verify -- deploy-evidence-20260526-120000.tar.gz --max-age-hours 24
npm run deploy:report:verify -- deploy-evidence-20260526-120000.tar.gz --max-age-hours 24 --summary deploy-health-acceptance.md --summary-json deploy-health-acceptance.json
npm run deploy:report:verify -- deploy-health-report.json --require-text deploy-health-report.txt --max-age-hours 24
```

`deploy:acceptance` 默认要求完整证据包或完整证据目录、报告不超过 24 小时；验收 `.tar.gz` 时还要求同名 `.tar.gz.sha256` 存在，并生成 `deploy-health-acceptance.md` 和 `deploy-health-acceptance.json`。默认验收会强制 `productionEvidence.finalConclusionReady=true`，因此退出码也能作为最终生产证据闭环判断。最终闭环还要求 `productionEvidence.backupInventoryReady=true`，即备份库存风险为低、最近一次备份恢复演练有效，并且备份目录没有残留 `.work` 临时工作目录。直接校验证据包时，验收器会同时确认健康报告、Compose 状态、API/Web 日志尾部、Docker/宿主机资源、网络监听、备份库存、版本/镜像追踪和 README 是否齐全，辅助证据内容必须符合预期结构，主健康报告 `deploy-health-report.json`、`manifest.json`、`README.txt` 和 `deployment-provenance.txt` 的证据批次 ID 必须一致，核心容器必须带 `image=`、`imageId=sha256:`、`status=`、`health=`、`restartPolicy=`、`restartCount=` 和 `oom=`，并按 `manifest.json` 校验关键文件 SHA-256，只允许固定白名单文件，拒绝包含 `.env`、额外文件或被篡改的证据包；`--max-age-hours 24` 可避免误用过期报告。加上 `--summary` 和 `--summary-json` 可自定义 Markdown 与 JSON 验收摘要路径，记录完成情况、必要检查、备份库存闭环和剩余风险。

完整通过条件、失败处理和剩余风险见 [部署健康验收清单](部署健康验收清单.md)。

修改一键部署、自检或证据包脚本后，先在仓库根目录执行 `npm run verify:deploy`，再执行生产证据包验收；发布前仍建议执行 `npm run verify:local`。

生产环境不要使用：

```text
localhost:5173
localhost:8000
localhost:5433
localhost:6380
npm run dev
```

这些只属于本地开发。

## 端口规范

| 端口   | 所属模式              | 用途                    |
| ------ | --------------------- | ----------------------- |
| `5173` | 本地开发              | Vite 前端开发服务       |
| `8000` | 本地开发              | Express 后端开发服务    |
| `5433` | 本地开发/本地容器测试 | PostgreSQL 暴露到宿主机 |
| `6380` | 本地开发/本地容器测试 | Redis 暴露到宿主机      |
| `3780` | 本地容器测试/生产     | Web 对外访问入口        |

不要使用 `5174`、`5175` 或其他临时端口作为开发入口。`5173` 被占用时，先停止旧的 Vite 进程，再重新启动 `5173`。

## 容器命名规范

本项目固定使用这些容器名：

```text
3dparthub-web
3dparthub-api
3dparthub-postgres
3dparthub-redis
```

不要再手动创建类似 `3dparthub-redis-6380` 的临时容器。现在 `docker-compose.local.yml` 已经把 Redis 映射到宿主机 `6380`。

如果历史上创建过临时 Redis 容器，确认不用后可以清理：

```bash
docker stop 3dparthub-redis-6380
docker rm 3dparthub-redis-6380
```

清理临时 Redis 不会影响 PostgreSQL 数据库。

## 常见问题

### 后端提示 Can't reach database server at localhost:5433

说明本地 PostgreSQL 没起来。执行：

```bash
colima start
docker compose -f docker-compose.local.yml up -d postgres
```

### 后端提示 Redis ECONNREFUSED localhost:6380

说明本地 Redis 没起来或没有映射端口。执行：

```bash
colima start
docker compose -f docker-compose.local.yml up -d redis
```

### 前端能打开但接口 502

通常是 Vite 代理目标不通、后端没启动，或后端连不上数据库。检查：

```bash
curl http://localhost:3780/api/health
curl http://localhost:5173/api/health
CHECK_VITE=1 node scripts/check-local-stack.mjs
docker ps
```

日常开发默认让 `5173` 代理本机后端 `8000`。只有做完整容器链路测试时，才访问 `3780`，不要把 `3780` 当成前端开发端口。

### Docker 提示 docker.sock 不存在

说明 Colima 没启动。执行：

```bash
colima start
```

### 什么时候重启后端

如果先启动了后端，后启动数据库或 Redis，后端里可能保留旧连接错误。依赖服务启动后，重启一次后端最干净：

```bash
cd server
npm run dev:local
```

## 给后续维护者的约定

1. 本地开发默认先启动 `postgres` 和 `redis`，再启动后端和前端。
2. 本地前端固定使用 `5173`，端口占用时必须先停掉旧进程，不允许自动换到 `5174`/`5175`。
3. 本地后端固定使用 `8000`，端口占用时必须先停掉旧进程。
4. 本地 PostgreSQL 固定使用 `5433`。
5. 本地 Redis 固定使用 `6380`。
6. 生产环境只使用 `docker-compose.yml`，不使用本地 `.env` 的 `localhost` 地址。
7. 不要删除数据库卷，除非明确要清空环境并且已经备份。
