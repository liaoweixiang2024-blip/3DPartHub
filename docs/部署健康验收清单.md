# 3DPartHub 生产部署健康验收清单

这份清单用于确认 Docker 一键部署、自检报告和证据包是否达到可上线/可排障状态。验收必须基于真实生产服务器当前生成的证据，不能使用旧报告或本地模拟报告代替。当前完成情况和剩余风险汇总见 [企业级改进验收状态](./企业级改进验收状态.md)。

## 生产服务器采集

在实际部署目录执行：

```bash
cd /opt/3dparthub
curl -fsSL -O https://raw.githubusercontent.com/liaoweixiang2024-blip/3DPartHub/main/scripts/collect-deploy-evidence.sh
sh collect-deploy-evidence.sh
```

最终生产结论默认要求“备份库存风险”为低，并且必须包含最近一次有效的备份恢复演练证据。采集最终证据前，先在维护窗口执行一次恢复演练：

```bash
cd /opt/3dparthub
docker compose exec api npm run backup:e2e
sh collect-deploy-evidence.sh
```

恢复演练会创建整站备份、导入为新备份记录、执行恢复，并对比恢复前后的数据库和业务文件指纹。成功后会在备份目录写入 `.restore-drills/latest.json`；证据包的 `backup-inventory.txt` 会显示 `Restore drill evidence: status=passed`，验收摘要会显示“备份恢复演练已执行”。如果缺少该证据、演练时间无效、最近演练超过 30 天，或备份目录残留 `.work` 临时工作目录，验收摘要会把 `backupInventory.riskLevel` 提升为中风险，`productionEvidence.finalConclusionReady` 不会为 `true`。该演练会真实触发恢复流程，生产环境只建议在维护窗口和外部副本都确认后执行。

如果生产环境不是默认目录、Compose 文件或 `.env` 文件名，需要显式指定：

```bash
sh collect-deploy-evidence.sh --compose-file /opt/3dparthub/docker-compose.yml --env-file /opt/3dparthub/.env
```

采集脚本不会重启服务或修改配置；除备份目录写入并删除一个隐藏探针文件外，只读取运行状态。输出目录必须为空；脚本会拒绝复用非空目录，避免新旧证据混在一起。

`collect-deploy-evidence.sh` 会调用同目录下的 `deploy-health-check.sh` 生成健康报告；如果生产服务器上还没有该脚本，采集脚本会自动下载官方仓库中的版本。需要单独复查健康报告时，也可以直接执行 `sh deploy-health-check.sh --report deploy-health-report.txt --json deploy-health-report.json`。

## 回传文件

优先回传生成的压缩包：

```text
deploy-evidence-YYYYMMDD-HHMMSS.tar.gz
deploy-evidence-YYYYMMDD-HHMMSS.tar.gz.sha256
```

`.sha256` 文件用于在传输后校验证据包归档本身是否损坏；生产验收 `.tar.gz` 时默认要求它与 `.tar.gz` 一起回传，验收器会先校验外层 SHA-256，并要求摘要文件中的文件名指向当前 `.tar.gz`，再校验证据包内部的 `manifest.json`。只有旧证据包确实遗失摘要文件时才使用 `--allow-missing-sidecar` 临时验收。如果无法回传压缩包，也可以回传完整证据目录。不要单独复制 `.env`；证据包本身会拒绝包含 `.env`。

采集脚本会对日志片段和命令输出中的常见密钥、连接串和 `Authorization` 头做敏感信息脱敏；验收器会再次扫描证据文本，发现明显的密钥赋值、带密码的连接串或未脱敏认证头时拒绝通过。

一键部署过程中如果服务启动失败、初始健康检查未通过或部署自检失败，脚本会自动尝试生成 `deploy-evidence-failed-YYYYMMDD-HHMMSS.tar.gz` 和同名 `.sha256`。该压缩包同样不包含 `.env`，需要把两份文件一起回传，并按同一套验收命令验证。

证据目录、健康报告和验收摘要包含主机名、部署目录、端口和日志片段，仓库默认已忽略 `deploy-evidence-*`、`deploy-health-report.*` 和 `deploy-health-acceptance.*`。需要归档时放到公司内部运维系统或私有资料库，不要随业务代码提交。

## 本地验收命令

先在仓库根目录执行部署专项验收，确认一键部署、自检报告、证据包采集和报告验收器没有本地问题：

```bash
npm run verify:deploy
```

提交或发布前再执行本地总验收，确认前后端构建、代码质量和 Compose 配置也通过：

```bash
npm run verify:local
```

拿到生产证据包后执行：

```bash
npm run deploy:acceptance -- deploy-evidence-YYYYMMDD-HHMMSS.tar.gz
npm run deploy:report:verify -- deploy-evidence-YYYYMMDD-HHMMSS.tar.gz --max-age-hours 24
npm run deploy:report:verify -- deploy-evidence-YYYYMMDD-HHMMSS.tar.gz --max-age-hours 24 --summary deploy-health-acceptance.md --summary-json deploy-health-acceptance.json
```

如果只回传了两份报告：

```bash
npm run deploy:acceptance -- deploy-health-report.json --require-text deploy-health-report.txt --allow-report-only
npm run deploy:report:verify -- deploy-health-report.json --require-text deploy-health-report.txt --max-age-hours 24
```

`deploy:acceptance` 默认要求完整证据包或完整证据目录、报告不超过 24 小时；验收 `.tar.gz` 时还要求同名 `.tar.gz.sha256` 存在，并生成 `deploy-health-acceptance.md` 和 `deploy-health-acceptance.json`。默认验收会强制 `productionEvidence.finalConclusionReady=true`，因此自动化只看退出码也不会把兜底报告、未闭环备份库存或缺少恢复演练的证据误判为最终生产结论。只有无法回传完整证据包时才使用 `--allow-report-only`，且必须同时传入 `--require-text deploy-health-report.txt`；这种模式不能证明 Compose 状态、API/Web 日志尾部、Docker/宿主机资源、网络监听、备份库存、版本/镜像追踪和 manifest 哈希未被篡改。只有旧证据包遗失摘要文件时才使用 `--allow-missing-sidecar`，这种模式不能证明归档在传输后仍与服务器生成时完全一致。通过完整证据包验收时，摘要会记录结论、环境快照、必要检查、证据完整性、备份库存闭环和剩余风险；如果同名 `.tar.gz.sha256` 已回传，Markdown 与 JSON 摘要会保留归档 SHA-256 摘要、摘要文件路径和匹配结果。JSON 摘要中的 `productionEvidence.finalConclusionReady` 用于标记该输入是否已经满足最终生产结论所需的证据闭环，方便后续归档、对比或接入后台。

## 通过条件

验收通过必须同时满足：

- 证据生成时间不超过 `24` 小时。
- JSON 报告 `schemaVersion` 为 `1`，结果为 `passed`，没有失败项和警告项。
- 必须通过 Docker daemon、Compose 配置、Compose 服务键去重、Compose 持久化挂载、Compose API 关键环境、Compose 镜像来源、Compose 资源限制、API 停止宽限期、Compose 内部网络、Compose 端口暴露、Compose Web 端口映射、Redis healthcheck `REDISCLI_AUTH` 认证 ping、实际容器挂载、容器资源限制、运行容器端口暴露、运行容器关键环境与 `.env` 一致性、API 主进程非 root 运行、`.env` 文件权限、数据库密码 `DB_PASSWORD`、Redis 密码 `REDIS_PASSWORD`、`JWT_SECRET`、`ADMIN_PASS`、生产来源 `ALLOWED_ORIGINS`、API CORS 允许来源运行时一致性、备份签名密钥 `BACKUP_SIGNING_SECRET`、备份加密密钥 `BACKUP_ENCRYPTION_SECRET`、`IMAGE_TAG` 与 api/web 运行镜像标签一致性、运行镜像来源、API 容器、宿主机端口监听、Web 容器端口映射、Web 敏感路径、健康接口、就绪接口、存活接口、管理健康接口访问控制、运行版本、API/Web 安全响应头、Web 首页入口、Web 前端静态资源、PostgreSQL 密码、数据库迁移状态、Redis 密码、资源配置预算、宿主机备份目录可写性、部署目录磁盘和 inode、Docker 数据目录磁盘和 inode、备份目录磁盘和 inode、API 数据卷容量、API 运行目录权限和 API/Web 日志扫描。
- 必要检查必须一项一条、位于 pass 信息开头、不能重复、不能把多个必要通过项合并到同一条 pass 信息里；验收器会拒绝重复、伪造前缀或拼接后的健康报告。
- 同时提供 `deploy-health-report.json` 和 `deploy-health-report.txt` 时，TXT 中的 Compose 文件、环境文件、证据批次和通过/警告/失败汇总必须与 JSON 一致，避免新旧报告混用。
- 核心容器不能缺少 healthcheck；自检发现 `health=none` 会记为“未配置 healthcheck”警告，默认生产验收会拒绝。
- 核心容器不能出现近期 OOMKilled 或重启次数较高；自检发现 `OOMKilled=true` 或 `restartCount` 过高会记为警告，默认生产验收会拒绝。
- `/api/health/deep` 这类管理健康接口不能未登录返回 `2xx`；自检会确认未登录访问只能返回 `401`、`403`、`404`、`405` 或登录重定向，避免公开数据库、Redis、存储和内部诊断信息。
- `/api/settings/version` 必须能返回当前运行版本；当 `.env` 锁定了具体 `IMAGE_TAG`（非 `latest` / `dev`）时，运行版本必须与该标签一致，避免更新后 Web/API 仍跑旧镜像。
- API 容器内的 Prisma `migrate status` 必须通过，证明当前镜像内的迁移文件与生产数据库一致；存在未应用迁移、迁移失败或 schema drift 时不能继续发布。
- API 主进程必须以非 root 用户运行；自检发现 `uid=0` 会记为失败，避免镜像入口脚本回退或被改动后扩大容器内文件写入和逃逸风险面。
- Compose 配置中 `api`、`web`、`postgres`、`redis` 必须声明 `healthcheck` 和 `restart: unless-stopped`，避免部署文件缺少健康探针或重启自恢复策略。
- Compose 配置中核心服务的关键服务键不能重复，避免 YAML 重复键被 Compose 解析覆盖后实际配置与人工预期不一致。
- Compose 配置中 `api.environment` 必须声明 `DATABASE_URL`、`REDIS_URL`、`JWT_SECRET`、`BACKUP_SIGNING_SECRET`、`BACKUP_ENCRYPTION_SECRET` 和 `ALLOWED_ORIGINS`，避免重建容器后丢失数据库、缓存、安全密钥或 CORS 配置。
- Compose 配置中 `api` 和 `web` 必须使用 3DPartHub API/Web 镜像，并且镜像标签与 `IMAGE_TAG` 一致，避免部署文件被改成错误镜像或旧镜像。
- 当前运行的 `api` 和 `web` 容器必须来自 3DPartHub GHCR 镜像仓库；运行镜像来源异常时不能继续发布，即使标签名称看起来正确。
- Compose 配置中 `api`、`web`、`postgres`、`redis` 必须声明 `mem_limit` 和 `cpus`，确保资源预算不只是 `.env` 里的建议值，而是真正进入容器资源控制。
- Compose 配置中 `api.stop_grace_period` 必须至少 `5m`，并且运行中的 API 容器 `StopTimeout` 必须至少 `300s`，避免备份、恢复、上传或转换任务在重启、升级或停机时被 Docker 过早终止。
- Compose 配置中 `api`、`web`、`postgres`、`redis` 必须绑定 `internal` 网络，并保留顶层 `networks.internal` 声明，避免核心服务脱离预期内部网络。
- Compose 配置中只有 `web` 可以发布宿主机端口；`api`、`postgres`、`redis` 不能声明 `ports`，避免 API、数据库或 Redis 被直接暴露到公网。
- 当前运行容器必须已经生效 `restart: unless-stopped`，避免只修改了 Compose 文件但没有重建容器，导致宿主机或 Docker 重启后服务无法自动恢复。
- 当前运行容器必须已经生效内存和 CPU 限制，并与 `.env` 资源预算一致，避免只修改了 Compose 或 `.env` 但没有重建容器。
- 当前运行容器中只有 `3dparthub-web` 可以绑定宿主机端口；`3dparthub-api`、`3dparthub-postgres`、`3dparthub-redis` 不能出现宿主机端口映射。
- Web 入口必须拒绝直接访问备份、原始模型、图纸、附件、HTML 预览、批量任务、上传目录和 X-Accel 内部下载路径；自检会写入临时探针文件并确认 `/static/backups/...`、`/static/originals/...`、`/static/drawings/...`、`/static/*-attachments/...`、`/static/html-previews/...`、`/static/batch/...`、`/static/_backup_db/...`、`/static/_safety_snapshots/...`、`/static/.restore_...`、`/uploads/...`、`/_protected_static/...` 与 `/_protected_uploads/...` 只能返回 `401`、`403` 或 `404`。
- API 容器内 `/app/uploads` 与 `/app/static` 数据卷的磁盘和 inode 必须充足，避免 Docker 数据目录整体看似可用但模型上传、转换预览或缩略图写入在容器内失败。
- 部署自检会读取 `server/static/backups/.restore-drills/latest.json` 并提示备份恢复演练证据是否缺失、异常或超过 30 天；该检查不会自动执行恢复演练，最终生产闭环仍要求维护窗口内手动执行 `docker compose exec api npm run backup:e2e`。
- Compose 配置和当前运行容器必须启用 `json-file` 日志轮转，并包含 `max-size` 与 `max-file`，避免 API/Web 或数据库日志长期增长占满生产磁盘。
- 证据包包含健康报告、Compose 状态、API/Web 日志尾部、Docker/宿主机资源、网络监听、备份库存、版本/镜像追踪、README 和 `manifest.json`。
- 备份库存必须包含备份目录、`directoryExists` 目录摘要、最近备份记录、归档是否存在、manifest 版本、哈希/签名字段是否存在、孤儿归档、`workDirs` 临时工作目录数量和最近恢复演练状态；验收摘要会把它汇总为 `backupInventory`、`riskLevel`、`nextActions`、`restoreDrillExecuted` 和 Markdown 表格项。证据采集本身只读，不会自动执行恢复演练。
- 备份库存采集必须按最近修改时间读取元数据和归档，并支持中文或含空格的备份文件名，避免生产证据因为文件名拆词而漏报、误报或把较旧备份排在前面。
- 最终生产结论要求 `backupInventory.riskLevel=low`、`productionEvidence.backupInventoryReady=true`，且最近恢复演练有效、备份目录没有残留 `.work` 临时工作目录；没有恢复演练、演练时间无效、超过 30 天或存在临时工作目录时，默认生产验收不会通过最终闭环。
- `manifest.json` 中记录的大小和 SHA-256 与证据文件完全一致。
- Compose 服务清单、Compose 状态、Docker 容器概览、Docker 存储概览和 README 必须符合预期结构，不能只是空壳文件。
- 主健康报告 `deploy-health-report.json`、`manifest.json`、`README.txt` 和 `deployment-provenance.txt` 必须包含一致的证据批次 ID，证明这些文件来自同一次采集。
- 同名 `.tar.gz.sha256` 必须存在，摘要文件名必须指向当前 `.tar.gz`，并且必须与证据包归档 SHA-256 一致；只有显式使用 `--allow-missing-sidecar` 时才允许旧证据包缺少摘要。
- `deployment-provenance.txt` 必须包含版本、Git、Compose、`.env` 文件名和核心容器镜像信息；`api`、`web`、`postgres`、`redis` 都必须包含 `image=`、`imageId=sha256:`、`status=`、`health=`、`restartPolicy=`、`restartCount=` 和 `oom=`，且不能包含密钥赋值。
- 证据包只包含固定白名单文件，不包含 `.env`、明显敏感信息、额外文件、重复报告、符号链接或不安全路径。

## 不通过时怎么处理

- `Docker daemon was not ready`：先确认 Docker 服务已启动，当前用户有 Docker 权限。
- `Deploy self-check failed`：终端会列出失败项；再查看 `deploy-health-report.txt` 的上下文、`api-logs-tail.txt` 和 `web-logs-tail.txt`。
- `Web 首页入口失败`：API 健康接口可能正常，但 web 镜像、Nginx 静态目录或反代入口没有返回前端 HTML；先检查 `3dparthub-web` 日志、`/healthz`、端口映射和是否被外部 nginx/宝塔错误接管。
- `端口 3780 当前有 nginx 监听`：宿主机端口可能被宝塔/nginx 占用，Docker Web 容器没有直接接管该端口；确认是否要保留反代，或释放端口后重建容器并重新采集证据。
- `宿主机端口 3780 未检测到监听`：Web 容器端口映射可能未生效、服务刚启动未完成或 `PORT` 配置不一致；检查 `docker compose ps`、端口映射和 `.env` 后重新采集证据。
- `Web 容器端口映射异常`：`3dparthub-web` 没有把 `.env` 中的 `PORT` 映射到容器 `80/tcp`，即使宿主机端口有监听也可能不是当前 Web 容器在服务；执行 `docker compose up -d --force-recreate web` 后重新采集证据。
- `Web 敏感路径暴露异常`：备份、原始模型、图纸、附件、HTML 预览、批量任务、上传目录或 X-Accel 内部下载路径可被 Web 直接下载；检查 `client/nginx.conf`、外部 nginx/宝塔反代、Web 容器静态目录映射、`internal` 配置和旧镜像，修复后执行 `docker compose up -d --force-recreate web` 并重新采集证据。
- `存活接口失败`：API 进程可能不可访问或运行时状态异常；先检查 `/api/health/live`、API 容器状态、API 内存和最近日志，再重启或重建 API 容器。
- `管理健康接口未受保护`：`/api/health/deep` 未登录返回 `2xx`，说明内部诊断信息可能可被外部读取；检查 API 路由鉴权、中间件、外部反代和旧镜像，修复后重建 API 容器并重新采集证据。
- `运行版本接口异常` 或 `运行版本与 IMAGE_TAG 不一致`：`/api/settings/version` 无法读取，或固定 `IMAGE_TAG` 时 API 返回版本不一致；检查 API 镜像是否已更新、`/app/VERSION` 是否存在，并执行 `docker compose pull && docker compose up -d --force-recreate api web` 后重新采集证据。
- `数据库迁移状态异常`：API 镜像内 Prisma migrations 与生产数据库不一致，可能有未应用迁移、迁移失败或 schema drift；先检查 API 容器日志、`npx prisma migrate status --schema prisma/schema.prisma` 输出和数据库备份，再执行受控迁移或回滚后重新采集证据。
- `API 主进程以 root 运行`：API 镜像或入口脚本没有按预期切换到 `node` 用户；检查 Dockerfile、`docker-entrypoint.sh` 和镜像标签，修复后重建 API 容器并重新采集证据。
- `API 安全响应头缺失或异常` 或 `Web 首页安全响应头缺失或异常`：检查 web Nginx、外部 Nginx/宝塔反代或安全中间件是否保留 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`，Web 首页还应保留 `Content-Security-Policy`。
- `Web 前端静态资源失败`：首页 HTML 已返回，但引用的 `/assets/*.js` 或 `/assets/*.css` 无法加载，浏览器可能白屏；检查 web 镜像构建产物、Nginx 静态资源路径、反代缓存和是否混用了旧镜像。
- `API 容器运行目录不可写或缺失`：检查 `/app/uploads`、`/app/static` 和 `/app/static/backups` 的 volume 挂载与权限，通常需要确认宿主机 `./server/static/backups` 存在并可被 API 容器写入。
- `API 数据卷容量不足`：API 容器内 `/app/uploads` 或 `/app/static` 的磁盘空间或 inode 不足，模型上传、转换、缩略图或临时文件可能失败；清理 Docker 卷、迁移数据目录或扩容后重新采集证据。
- `备份恢复演练证据缺失`、`备份恢复演练证据异常` 或 `备份恢复演练证据已超过 30 天`：当前证据还不能证明备份可恢复；在维护窗口执行 `docker compose exec api npm run backup:e2e`，确认 `.restore-drills/latest.json` 更新后重新采集证据。
- `Web 最近日志包含常见入口错误`：Web 容器可能有 Nginx 配置、静态目录、上游连接或权限问题；检查 `web-logs-tail.txt`、`docker compose logs web --tail=180` 和外部反代配置。
- `宿主机备份目录不可写`：检查 `./server/static/backups` 的宿主机权限、挂载状态和磁盘只读状态；修复后重新采集证据。
- `Compose 持久化挂载缺失`：检查 `docker-compose.yml` 中 `pgdata`、`uploads-data`、`static-data`、`redis-data` 以及 `./server/static/backups:/app/static/backups` 是否还在；修复后重新部署并采集证据。
- `Compose 服务键重复`：检查 `docker-compose.yml` 中 `api`、`web`、`postgres`、`redis` 是否存在重复的 `restart`、`image`、`volumes`、`healthcheck` 等关键键；清理重复键后重新采集证据。
- `Compose API 关键环境缺失`：检查 `docker-compose.yml` 的 `api.environment` 是否仍传入数据库连接、Redis 连接、JWT、备份签名/加密密钥和 API CORS 允许来源；修复 Compose 后执行 `docker compose up -d --force-recreate api` 并重新采集证据。
- `Compose 镜像来源异常`：检查 `docker-compose.yml` 中 `api` / `web` 是否仍指向 3DPartHub API/Web 镜像，并确认 `.env` 的 `IMAGE_TAG` 是预期版本；修复后执行 `docker compose pull && docker compose up -d --force-recreate` 并重新采集证据。
- `Compose 资源限制缺失`：检查 `docker-compose.yml` 中核心服务是否仍声明 `mem_limit` 和 `cpus`；补齐后执行 `docker compose up -d --force-recreate`，避免 API、数据库、Redis 或 Web 容器无上限抢占低配服务器资源。
- `Compose API 停止宽限期缺失或过短` 或 `API 停止宽限期过短`：API 容器停机时可能无法给备份、恢复、上传或转换任务足够收尾时间；确认 `docker-compose.yml` 中 `api.stop_grace_period: 5m` 仍存在，并执行 `docker compose up -d --force-recreate api` 后重新采集证据。
- `Compose 内部网络缺失`：检查 `api`、`web`、`postgres`、`redis` 是否仍绑定 `internal` 网络，并确认顶层 `networks.internal` 未被删除；修复后执行 `docker compose up -d --force-recreate` 并重新采集证据。
- `Compose 端口暴露异常`：检查 `api`、`postgres`、`redis` 是否误加了 `ports`；这些服务只能走 Docker 内部网络，移除后执行 `docker compose up -d --force-recreate` 并重新采集证据。
- `Compose Redis healthcheck 未使用认证 ping`：Redis 已配置 `requirepass`，healthcheck 必须通过 `REDISCLI_AUTH` 执行 `redis-cli ping`；否则容器会在生产环境反复 unhealthy，修复 Compose 后重新部署并采集证据。
- `Compose Web 端口映射缺失或异常`：`docker-compose.yml` 中 `web.ports` 没有把 `.env` 的 `PORT` 映射到容器 `80/tcp`；修复 Compose 后执行 `docker compose up -d --force-recreate web` 并重新采集证据。
- `Compose 日志轮转未完整配置` 或 `容器日志轮转未完整生效`：检查 `docker-compose.yml` 中核心服务的 `logging` 配置是否包含 `driver: json-file`、`max-size` 和 `max-file`；修复后执行 `docker compose up -d --force-recreate`，避免日志占满磁盘。
- `资源配置超过当前内存档位`：`.env` 中的 API/数据库/Redis/Web 内存上限、API worker、转换并发、数据库连接数或 Redis maxmemory 对当前服务器过高；执行 `sh scripts/tune-resources.sh .env` 或重新运行一键部署生成匹配档位后，重建容器并重新采集证据。
- `容器挂载缺失或读写状态异常`：Compose 配置可能已经修复，但当前容器仍是旧挂载或 web 读写状态错误；执行 `docker compose up -d --force-recreate` 后重新采集证据。
- `容器资源限制未完整生效或与 .env 不一致`：Compose 配置可能已经补齐 `mem_limit` / `cpus`，或 `.env` 资源预算已经调整，但当前容器仍是旧资源配置；执行 `docker compose up -d --force-recreate` 后重新采集证据。
- `运行容器端口暴露异常`：当前容器仍把 API、PostgreSQL 或 Redis 绑定到了宿主机端口；确认 Compose 已移除私有服务 `ports` 后执行 `docker compose up -d --force-recreate` 并重新采集证据。
- `容器环境与 .env 不一致` 或 `容器启动参数与 .env 不一致`：`.env` 已修改但容器仍使用旧数据库密码、Redis 密码、JWT 密钥、备份签名密钥或备份加密密钥；确认数据库密码迁移完成后执行 `docker compose up -d --force-recreate`，再重新采集证据。
- `容器环境与 .env 不一致: API CORS 允许来源`：`ALLOWED_ORIGINS` 已修改但 API 容器仍使用旧来源配置，可能导致跨域或反代访问异常；执行 `docker compose up -d --force-recreate api` 后重新采集证据。
- `备份签名密钥 BACKUP_SIGNING_SECRET 未设置` 或 `备份加密密钥 BACKUP_ENCRYPTION_SECRET 未设置`：生产备份缺少独立签名或加密密钥；执行最新版一键部署脚本补齐 `.env`，或手动生成 32 字节以上随机值并重建 API 容器。
- `备份目录磁盘剩余不足 5GB`：备份目录所在磁盘空间不足，创建整站备份、恢复安全快照和导入大模型时风险较高；清理旧备份或扩容后重新采集证据。
- `Docker 数据目录磁盘剩余不足`：Docker 镜像、容器层、volume 或容器日志所在磁盘空间不足；执行 `docker system df` 定位占用，清理不用镜像/容器/日志或迁移 Docker data-root 后重新采集证据。
- `Docker 数据目录 inode 剩余不足`：Docker data-root 可创建文件数接近耗尽，可能导致拉镜像、创建容器、写入 volume 或日志失败；清理无用镜像/容器层/volume 后重新采集证据。
- `备份目录 inode 剩余偏低` 或 `部署目录 inode 剩余偏低`：目录所在文件系统可创建文件数接近耗尽，即使磁盘容量还有剩余，也可能无法写入模型、预览图、备份或临时文件；清理大量小文件或迁移到 inode 更充足的磁盘后重新采集证据。
- `deploy-evidence-failed-...`：一键部署启动失败、初始健康检查未通过或部署自检失败时自动生成的证据包，优先回传该文件排查。
- `has warnings`：终端会列出警告项；生产发布前不要忽略，除非是明确可接受的临时风险，并在复查时使用 `--allow-warnings`。
- `未配置 healthcheck`：容器可以运行但缺少健康探针，生产验收默认不通过；检查 `docker-compose.yml` 中 `api`、`web`、`postgres`、`redis` 的 `healthcheck` 配置后重新部署并采集证据。
- `未设置 restart: unless-stopped`：服务缺少 Docker 自恢复策略，宿主机或 Docker 重启后可能不会自动恢复；补齐 Compose 配置后重新部署并采集证据。
- `容器重启策略未完整生效`：Compose 已配置但运行容器仍未使用 `unless-stopped`；执行 `docker compose up -d --force-recreate` 后重新采集证据。
- `OOMKilled` 或 `重启次数较高`：容器近期可能被内存限制杀掉或反复重启；查看 `api-logs-tail.txt`、`web-logs-tail.txt`、`docker ps`、`docker stats`，必要时降低并发或调整资源上限后重新采集证据。
- `环境文件权限过宽`：`.env` 可能被其他系统用户读取，执行 `chmod 600 .env` 后重新采集证据。
- `数据库密码 DB_PASSWORD 未设置/使用默认值`、`Redis 密码 REDIS_PASSWORD 未设置/使用默认值`、`JWT_SECRET 未设置/使用默认值` 或 `ADMIN_PASS 使用默认值`：生成新的强随机值，确认旧数据库密码迁移或管理员账号策略后重建容器并重新采集证据。
- `ALLOWED_ORIGINS 包含 localhost 或通配符`：生产环境应留空走同源反代，或设置为真实域名/IP；修复 `.env` 后重建 API 容器并重新采集证据。
- `运行镜像标签与 IMAGE_TAG 不一致`：api/web 容器还在跑旧标签或非预期标签，执行 `docker compose pull && docker compose up -d --force-recreate` 后重新采集证据。
- `运行镜像来源异常`：api/web 容器不是来自 3DPartHub GHCR 镜像仓库，可能是 Compose 被改、手动替换镜像或本地同名镜像误用；确认 `docker-compose.yml`、`.env` 和镜像来源后执行 `docker compose pull && docker compose up -d --force-recreate`，再重新采集证据。
- `older than 24 hours`：重新在生产服务器采集证据包。
- `manifest.json ... mismatch`：证据文件采集后被修改或传输损坏，重新采集并回传。
- `bundleId is missing`、`evidenceBundleId` 或 `Evidence bundle ID`：证据批次 ID 缺失或不一致，通常是手动拼包或混用了不同批次文件，重新采集完整证据包。
- `missing valid imageId`：版本/镜像追踪信息不完整，通常是手动修改了 `deployment-provenance.txt` 或 Docker inspect 信息缺失，重新采集完整证据包。
